# NW-003.13.7 — Registration OTP Email Diagnostic Report

**Date:** 2026-08-26  
**Tester:** Cascade (diagnostic instance on port 8081)  
**Test account used:** Diagnostic account (email masked: `ot***om`)

---

## 1. Backend Log Flow (One Fresh Registration Attempt)

A fresh registration was submitted to `POST /api/v1/auth/register` on the diagnostic backend.

The observed flow is:

1. **Registration request received** — `POST /api/v1/auth/register` accepted.
2. **User persisted** — a new `PENDING` user record created.
3. **OTP generated** — `OtpService.requestOtp` generated an OTP for `purpose=REGISTRATION`.
4. **OTP persisted/hashed** — `OtpChallenge` saved with `otp_hash` and `expires_at`.
5. **OTP provider invoked** — `StubOtpProvider.sendEmail(...)` called with `purpose=REGISTRATION`.
6. **Email provider invoked** — no real email provider is present; only the stub logged the event.
7. **Provider response received** — none; there is no external provider to return a response.

Log evidence:

```
[STUB OTP] email=ot***om purpose=REGISTRATION otp=<REDACTED> otpId=<REDACTED>
```

> The actual OTP value is not shown in this report. The stub implementation logs it to the console.

---

## 2. OTP Provider

- **Active property:** `neowallet.otp.provider`
- **Configured value:** `stub` (default from `application.yml` and `application-dev.yml`)
- **Active implementation:** `com.neowallet.provider.stub.StubOtpProvider`
- **Activation condition:** `@ConditionalOnProperty(prefix = "neowallet.otp", name = "provider", havingValue = "stub", matchIfMissing = true)`

No environment variable was detected overriding `NEOWALLET_OTP_PROVIDER`, so the JVM fell back to the default `stub` value.

---

## 3. Email Provider

The MVP does **not** have a real email provider configured. The only active implementation is `StubOtpProvider`, which:

- accepts the `sendEmail(...)` call,
- masks the recipient address (first 2 and last 2 characters),
- logs the OTP to the backend console,
- performs no network call to any email/SMTP/SMS gateway.

There is no `spring.mail`, SendGrid, AWS SES, Mailgun, or Twilio configuration in the current active profile.

## 5. Provider Response Classification

The external email provider response is classified as:

**NOT CONFIGURED**

Reason: the active `StubOtpProvider` is not backed by any external email service, so no `SENT`, `REJECTED`, `FAILED`, `TIMEOUT`, or other real provider response exists.

---

## 6. Email Delivery

Because no real email provider is configured, the OTP was **not submitted** to any email delivery infrastructure. Therefore, there is no delivery confirmation, provider delivery log, or message ID.

If a real provider is later configured and reports `SENT`, delivery still depends on factors outside the application:

- spam/junk folder on the recipient side,
- sender/domain verification with the provider,
- recipient address validity,
- provider-specific delivery logs.

---

## 7. Final Diagnosis

**Root cause:**  
The backend OTP provider is set to `stub` (the default). The active `StubOtpProvider` only logs the generated OTP to the console and does not send any real email. The OTP is generated, persisted, and the provider is invoked, but no email is ever dispatched because there is no real email gateway configured.

```
Provider:                  StubOtpProvider (neowallet.otp.provider=stub)
Provider configured:       YES (the stub provider is active)
OTP generated:             YES
OTP persisted:             YES
Email submission attempted: YES (stub sendEmail was called)
Email provider response:   NOT CONFIGURED
Recommended fix:           Configure a real OTP/email provider implementation (e.g., SMTP, SendGrid, AWS SES, or Mailgun), set NEOWALLET_OTP_PROVIDER to that provider's key, and supply required credentials/secrets via environment variables. Do not modify application code until the Product Owner approves.
```
