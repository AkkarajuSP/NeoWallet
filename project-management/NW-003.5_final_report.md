# NW-003.5 — NeoWallet Financial Overview Final Report

## 1. Scope

Implementation of the Financial Overview / NeoWallet planning container, including the database schema, backend domain, and Flutter mobile screen. The work strictly follows the approved authoritative documents and product boundaries:

- NeoWallet does **not** hold customer funds, stored-value balances, PPI, custodial balances, execute payments, perform money movement, or provide wallet-to-wallet transfers.
- All financial values in this work are **planning/management values** unless explicitly identified as actual or pending records.
- The UI and API clearly distinguish **PLANNING**, **ACTUAL**, and **PENDING** records.
- All monetary values use `BigDecimal` in Java and `NUMERIC(15,2)` in PostgreSQL.
- Only the existing Financial Overview endpoints defined in `NeoWallet_OpenAPI_v1.yaml` were implemented.
- Family-aware access reuses the approved Family Management authorization model.

## 3. Database Migration

Migration `V6__financial_overview.sql` creates four tables under the `neowallet` schema:

1. **categories** — system and user-defined budget categories.
2. **financial_overviews** — consolidated planning/actual/pending values for a user or family for a period.
3. **financial_periods** — period boundaries for an overview.
4. **financial_allocations** — per-category allocated and actual amounts.

All monetary columns are `NUMERIC(15,2)`. Indexes, constraints, and default essential/variable/discretionary/savings categories are seeded. No V1–V5 migrations were modified.

## 4. API Endpoints Implemented

All endpoints are `GET /api/v1/financial-overview/...` and use JWT authentication. An optional `X-Family-ID` header triggers family-scoped access.

| Method | Path | Description |
|--------|------|-------------|
| GET | `/api/v1/financial-overview` | Full financial overview (planning, actual, pending, capacity) |
| GET | `/api/v1/financial-overview/summary` | Income / expenses / savings / adherence summary |
| GET | `/api/v1/financial-overview/allocations` | Per-category allocations and utilization |
| GET | `/api/v1/financial-overview/commitments` | Committed amounts |
| GET | `/api/v1/financial-overview/pending` | Pending payments |
| GET | `/api/v1/financial-overview/capacity` | Available Financial Capacity with disclaimer |

## 5. Planning vs. Actual vs. Pending Model

- **Planning values**: `planningIncome`, `essentialAllocation`, `savingsAllocation`, `emergencyAllocation`, `discretionaryPlanning`, `availableFinancialCapacity`.
- **Actual records**: `actualTransactions`.
- **Pending records**: `pendingPayments`.
- **Committed amounts**: `committedAmount` and `mandatoryCommitments`.

The API response and mobile UI label sections explicitly as "Planning Values", "Actual & Pending Records", and "Available Financial Capacity". A disclaimer is included to avoid any suggestion of held funds.

## 6. Calculation Rules

Available Financial Capacity is stored as `available_financial_capacity` in the database and returned directly. The summary endpoint computes:

- `totalIncome` = `planningIncome`
- `totalExpenses` = `committedAmount` + `actualTransactions`
- `totalSavings` = `savingsAllocation` + `emergencyAllocation`
- `availableCapacity` = `availableFinancialCapacity`
- `budgetAdherence` = `actualTransactions * 100 / totalAllocation` rounded to 2 decimal places (0 if total allocation is 0)

All calculations use `BigDecimal` with `RoundingMode.HALF_UP` where division occurs.
