# NW-003.6 — NeoWallet Transaction Management Final Report

## 1. Scope

Implementation of the Transaction Management capability, including recording, viewing, updating, deleting, listing, filtering, and categorizing actual financial transactions. This work strictly follows the approved product boundaries:

- NeoWallet MVP does **not** execute payments, move money, or hold customer funds.
- Transactions are financial **records/representations** only.
- No payment gateway, UPI, P2P, wallet transfer, cash-out, add-money, or withdraw-money functionality was introduced.
- Monetary values use `BigDecimal` in Java and `NUMERIC(15,2)` in PostgreSQL.
- Family authorization reuses the approved Family Management model.
- Only the transaction endpoints already defined in `NeoWallet_OpenAPI_v1.yaml` were implemented.

## 3. Database Migration

**V7__transactions.sql** creates the `neowallet.transactions` table with the following columns:

`transaction_id`, `user_id`, `family_id`, `family_member_id`, `type`, `category_id`, `category_name`, `amount`, `currency`, `description`, `transaction_date`, `posted_date`, `status`, `is_recurring`, `recurring_pattern`, `external_reference`, `source`, `created_at`, `updated_at`, `deleted_at`.

All monetary columns are `NUMERIC(15,2)`. `CHECK` constraints enforce the approved type, status, and source values. Soft delete is supported via `deleted_at`. No V1–V6 migrations were modified.

## 4. Transaction Types and Statuses

**Types** (from OpenAPI/Business Rules):
- `INCOME` — money received
- `EXPENSE` — money spent
- `REFUND` — money returned
- `ADJUSTMENT` — manual adjustment
- `TRANSFER_RECORD` — transfer record only

**Statuses**:
- `PLANNED`, `COMMITTED`, `PENDING`, `COMPLETED`, `FAILED`, `REVERSED`

## 5. API Endpoints Implemented

| Method | Path | Description |
|--------|------|-------------|
| POST | `/api/v1/transactions` | Create a transaction |
| GET | `/api/v1/transactions` | List transactions with pagination and filtering |
| GET | `/api/v1/transactions/{transactionId}` | Get a transaction by ID |
| PUT | `/api/v1/transactions/{transactionId}` | Update a transaction |
| DELETE | `/api/v1/transactions/{transactionId}` | Soft-delete a transaction |

All endpoints use `bearerAuth`. `X-Family-ID` header is optional for family-scoped operations.

## 6. Filtering

The list endpoint supports the approved filters:

- `filterCategory` (category name)
- `filterType` (transaction type)
- `filterStatus` (transaction status)
- `filterFamilyMemberId` (family member UUID)
- `filterAmountFrom` / `filterAmountTo`
- `filterDateFrom` / `filterDateTo`

Plus pagination (`page`, `limit`) and `sort`.

## 7. Authorization Model

- `X-Family-ID` is treated as a resource selector only.
- Server-side membership is verified via `FamilyMemberRepository.existsByFamily_FamilyIdAndUser_UserIdAndLeftAtIsNull`.
- A transaction can only be accessed, updated, or deleted by its owner or an active member of its family.
- Non-members and cross-family manipulation are rejected with `403`.

## 8. CRUD Behavior

- **Create**: stores the record with `source = MANUAL`, validates type, status, currency, and positive amount.
- **Read**: returns the record for the owner or authorized family member.
- **Update**: allowed with audit trail. Cannot update `COMPLETED` or deleted records.
- **Delete**: soft delete (`deleted_at` set). Cannot delete `COMPLETED` or already-deleted records.

## 9. Audit

All create, update, and delete operations record an `AuditLog` entry with the actor, action, resource type, and a JSON metadata payload containing key fields (type, amount, currency, status, category). Old and new values are preserved for updates.

## 10. Financial Overview Integration

Transaction records remain a separate domain. The `Transaction` entity uses the same `categories` table as NW-003.5. No transaction data is duplicated into `financial_overviews`; future Financial Overview recalculation can query `transactions` deterministically. No AI is used for authoritative calculations.
