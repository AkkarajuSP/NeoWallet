# NW-003.8.1 — Savings Authorization Role Verification

## Objective
Verify whether `ADMIN` has been introduced as an actual NeoWallet **family role**, or whether it exists only as an internal/system authorization concept. Approved product family roles are: `OWNER`, `MEMBER`, `RESTRICTED`.

## Method
Searched the `neowallet` backend and Flutter application for case-sensitive `ADMIN` occurrences, then inspected:
- Java entities, DTOs, service authorization logic, and controllers
- Flyway database migrations and constraints
- Flutter data models
- Test sources
- OpenAPI and project documentation

## Verdict

**`ADMIN` is NOT an actual NeoWallet family role in the product model.**

The only valid family roles that can be stored or assigned are:
- `OWNER`
- `MEMBER`
- `RESTRICTED`

`ADMIN` does appear in two places in the production family authorization flow, but as an **unreachable internal authorization constant**, and in one unrelated database constraint for audit logs. It is not introduced as a new product role.

## Exact Locations of `ADMIN`

### 1. Family authorization logic (internal, dead code path)
- `neowallet/backend/neowallet-api/src/main/java/com/neowallet/finance/service/BudgetService.java:458`
  - `if (!List.of("OWNER", "ADMIN").contains(member.getRole())) { ... }`
- `neowallet/backend/neowallet-api/src/main/java/com/neowallet/finance/service/SavingsGoalService.java:215`
  - `if (!List.of("OWNER", "ADMIN").contains(member.getRole())) { ... }`

These methods (`ensureWriteAccess` and `findAndEnsureWriteAccess`) allow budget/savings-goal updates when the acting family member's role is `OWNER` **or `ADMIN`**. However, because the family domain never permits a `family_members.role` of `ADMIN`, the `ADMIN` branch is effectively unreachable and the check reduces to `OWNER` only.

### 2. Audit-log actor type (unrelated system concept)
- `neowallet/backend/neowallet-api/src/main/resources/db/migration/V2__identity.sql:113`
  - `CONSTRAINT chk_audit_logs_actor_type CHECK (actor_type IN ('USER', 'SYSTEM', 'ADMIN'))`

This is a system-level `actor_type` for audit logging, not a family role.

### 3. Report wording (imprecise reference)
- `NW-003.8_final_report.md:51`
  - `Updates/deletes restricted to family OWNER/ADMIN.`

This wording conflates the authorization checks in `BudgetService`/`SavingsGoalService` with the actual product family roles.

## Where `ADMIN` is NOT Found

| Area | Finding |
|------|---------|
| **Java entity** | `FamilyMember.java` uses a plain `String role` with default `"MEMBER"`. No `ADMIN` constant or enum. |
| **Enums** | No `FamilyRole` enum exists; roles are validated as string lists in `FamilyService`. `VALID_FAMILY_ROLES = List.of("OWNER", "MEMBER", "RESTRICTED")`. |
| **Family service authorization** | `FamilyService.java:26` only accepts `OWNER`, `MEMBER`, `RESTRICTED`. `INVITABLE_ROLES` and `MUTABLE_ROLES` exclude `ADMIN`. |
| **Database family constraints** | `V5__family_members_invitations.sql:12` enforces `role IN ('OWNER', 'MEMBER', 'RESTRICTED')`. Invitations are limited to `MEMBER`/`RESTRICTED`. |
| **API DTOs** | `FamilyInvitationRequest`, `UpdateFamilyMemberRequest`, and `FamilyMemberResponse` use plain `String role`; no `ADMIN` in validation or schemas. |
| **Flutter models** | `lib/features/family/models/family_models.dart` uses `String role`; no `ADMIN` value. |
| **Tests** | No `ADMIN` occurrences in `neowallet/backend/neowallet-api/src/test`. |
| **OpenAPI family role schemas** | `NeoWallet_OpenAPI_v1.yaml` mentions `ADMIN` only in `403` response descriptions for system admin endpoints, not in the family role schema. |

## Why the `ADMIN` Branch Exists

The `BudgetService` and `SavingsGoalService` write-guard code was written to mirror the report statement `"OWNER/ADMIN only for writes"`. It appears to be a placeholder for an administrative override concept, but because the family domain does not model `ADMIN`, the branch can never be satisfied by real data. The current implementation therefore allows only `OWNER` to perform budget/savings-goal writes.

## Conclusion

- `ADMIN` has **not** been introduced as an actual family role in the NeoWallet product.
- It is only an **internal authorization string** in two finance service checks and an unrelated **audit-log `actor_type`**.
- The approved family role set (`OWNER`, `MEMBER`, `RESTRICTED`) remains intact in entities, service logic, DTO validation, database constraints, and Flutter models.

No code was changed for this verification. NW-003.9 was not started.
